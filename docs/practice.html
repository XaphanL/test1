Горутины и синхронизация

Как думать над задачей

  1. Нарисуй горутины и каналы стрелками.
  2. Для каждой операции спроси: она может заблокироваться?
  3. Определи владельца close.
  4. Продумай отмену и условие завершения.
01Запуск и ожидание горутинgo + sync.WaitGroup

Условие

Запусти три вызова work конкурентно и дождись каждого. Порядок вывода не фиксирован.

func work(id int) { fmt.Println("worker", id) }

func main() {
    // work(1), work(2), work(3) конкурентно
}
  • Add должен выполняться до запуска горутины.
  • Каждый worker обязан сообщить о завершении.

Решение

var wg sync.WaitGroup
for i := 1; i <= 3; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        work(id)
    }(i)
}
wg.Wait()

Почему: Wait блокирует main, пока счётчик не станет нулём. WaitGroup ждёт выполнение, но не защищает общие данные.

02Результат через каналНебуферизованный channel

Условие

Вычисли квадрат числа в горутине и передай результат в main через канал.

func square(n int, out chan<- int) {
    // отправь n * n
}

Решение

func square(n int, out chan<- int) { out <- n * n }

result := make(chan int)
go square(7, result)
fmt.Println(<-result) // 49

Почему: send и receive на небуферизованном канале встречаются и синхронизируют две горутины. Для одного чтения закрывать канал необязательно.

03Кто закрывает канал?close + range

Условие

Producer отправляет числа 1…5. Consumer читает их через range и должен завершиться.

func produce(out chan<- int) {
    for i := 1; i <= 5; i++ { out <- i }
    // чего не хватает?
}

Решение

func produce(out chan<- int) {
    defer close(out)
    for i := 1; i <= 5; i++ { out <- i }
}

ch := make(chan int)
go produce(ch)
for v := range ch { fmt.Println(v) }

Почему: канал закрывает отправитель — именно он знает, что новых значений не будет. range дочитает буфер и завершится.

04Буфер и backpressureОграниченная очередь

Условие

Создай очередь максимум на три задания. Если consumer отстаёт, producer должен ждать.

type Job struct{ ID int }
jobs := make(chan Job, /* размер */)

Решение

jobs := make(chan Job, 3)
go func() {
    defer close(jobs)
    for i := 1; i <= 10; i++ {
        jobs <- Job{ID: i}
    }
}()
for job := range jobs { handle(job) }

Почему: пока в буфере есть место, producer идёт дальше. Когда три места заняты, следующий send ждёт consumer — это естественное обратное давление.

05Ожидание через selectРезультат или timeout

Условие

Получи результат, но не жди дольше 500 мс. Таймер должен корректно освобождаться.

func wait(result <-chan string) {
    // result или timeout
}

Решение

func wait(result <-chan string) {
    timer := time.NewTimer(500 * time.Millisecond)
    defer timer.Stop()
    select {
    case v := <-result:
        fmt.Println(v)
    case <-timer.C:
        fmt.Println("timeout")
    }
}

Почему: select ждёт готовый case. default здесь не нужен: в цикле он создал бы активное ожидание и нагрузку на CPU.

06Отмена через contextУправление жизненным циклом

Условие

Worker обрабатывает задания, пока не отменён context или не закрыт входной канал.

func worker(ctx context.Context, jobs <-chan Job) {
    for { /* жди ctx.Done() или jobs */ }
}

Решение

func worker(ctx context.Context, jobs <-chan Job) {
    for {
        select {
        case <-ctx.Done():
            return
        case job, ok := <-jobs:
            if !ok { return }
            handle(job)
        }
    }
}

Почему: ctx.Done() закрывается при отмене. Проверка ok не даёт бесконечно читать zero value из закрытого канала.

07Фиксированный worker poolЧетыре постоянных worker

Условие

Обработай 100 задач максимум четырьмя workers и собери результаты. results закрой только после завершения всех отправителей.

func worker(jobs <-chan Job, results chan<- Result) {
    for job := range jobs { results <- process(job) }
}

Решение

jobs := make(chan Job)
results := make(chan Result)
var wg sync.WaitGroup
for i := 0; i < 4; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        worker(jobs, results)
    }()
}
go func() { wg.Wait(); close(results) }()
go func() { defer close(jobs); sendJobs(jobs) }()
for r := range results { save(r) }

Почему: четыре workers задают лимит активной обработки. Отдельная closer-горутина ждёт всех отправителей, пока main одновременно читает результаты.

08Лимит через семафорНе более пяти операций

Условие

Для каждого URL запусти горутину, но разреши одновременно выполнять максимум пять запросов.

func fetchAll(urls []string) {
    sem := make(chan struct{}, /* лимит */)
}

Решение

func fetchAll(urls []string) {
    sem := make(chan struct{}, 5)
    var wg sync.WaitGroup
    for _, url := range urls {
        wg.Add(1)
        go func(u string) {
            defer wg.Done()
            sem <- struct{}{}
            defer func() { <-sem }()
            fetch(u)
        }(url)
    }
    wg.Wait()
}

Почему: шестая горутина ждёт свободный слот. В отличие от worker pool, горутин может быть много, но одновременно выполняется не больше пяти запросов.

09Объединение потоков fan-inНесколько входов → один выход

Условие

Объедини произвольное число входных каналов в один. Закрой выход после исчерпания всех входов.

func merge(inputs ...<-chan int) <-chan int {
    out := make(chan int)
    // copier для каждого input
    return out
}

Решение

func merge(inputs ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    wg.Add(len(inputs))
    for _, in := range inputs {
        go func(ch <-chan int) {
            defer wg.Done()
            for v := range ch { out <- v }
        }(in)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

Почему: отдельный copier читает каждый источник. Порядок между источниками не гарантирован, а выход закрывается ровно после последнего copier.

10Безопасный pipelineОтмена без утечки горутин

Условие

Построй стадию square. Если sink прекратил чтение, context должен разблокировать и чтение, и отправку результата.

func square(ctx context.Context, in <-chan int) <-chan int {
    out := make(chan int)
    // стадия pipeline
    return out
}

Решение

func square(ctx context.Context, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for {
            select {
            case <-ctx.Done():
                return
            case v, ok := <-in:
                if !ok { return }
                select {
                case out <- v * v:
                case <-ctx.Done(): return
                }
            }
        }
    }()
    return out
}

Почему: проверять отмену нужно и вокруг потенциально блокирующего send. Стадия владеет своим out и закрывает его при завершении.

Каналы и пакет sync

Как выбрать примитив

  1. Канал — передача данных и владения.
  2. Mutex — составное изменяемое состояние.
  3. Atomic — независимое простое значение.
  4. WaitGroup — ожидание фактического завершения.
11Счётчик под MutexMutex + WaitGroup

Условие

100 горутин увеличивают общий счётчик по 1000 раз. Получи строго 100000 без data race.

var counter int
// 100 goroutine: counter++

Решение

var counter int
var mu sync.Mutex
var wg sync.WaitGroup
for i := 0; i < 100; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for j := 0; j < 1000; j++ {
            mu.Lock(); counter++; mu.Unlock()
        }
    }()
}
wg.Wait()
fmt.Println(counter)

Почему: Mutex делает изменение взаимоисключающим, а WaitGroup гарантирует чтение после всех записей. Это разные задачи синхронизации.

12Счётчик через atomicatomic.Int64 + channel

Условие

Workers читают jobs. Посчитай число обработанных заданий без Mutex и дождись всех workers.

var processed atomic.Int64
jobs := make(chan Job)

Решение

var wg sync.WaitGroup
for i := 0; i < 4; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for job := range jobs {
            handle(job)
            processed.Add(1)
        }
    }()
}
sendJobs(jobs); close(jobs)
wg.Wait()
fmt.Println(processed.Load())

Почему: Add — атомарный read-modify-write. Atomic подходит для независимого числа, но не для нескольких связанных полей.

13Один владелец mapChannel ownership

Условие

Несколько producers создают события. Одна goroutine должна собрать частоты в map без Mutex.

events := make(chan string)
// producers → aggregator → result

Решение

result := make(chan map[string]int, 1)
go func() {
    counts := make(map[string]int)
    for e := range events { counts[e]++ }
    result <- counts
}()
for _, src := range sources {
    wg.Add(1)
    go func(s Source) {
        defer wg.Done(); s.Send(events)
    }(src)
}
go func() { wg.Wait(); close(events) }()
counts := <-result

Почему: map принадлежит только aggregator. WaitGroup определяет момент закрытия общего канала событий.

14Кэш под RWMutexМного readers, один writer

Условие

Много goroutine читают кэш, одна обновляет его из канала. Сделай Get и Set безопасными.

type Cache struct {
    mu sync.RWMutex
    m  map[string]string
}

Решение

func (c *Cache) Get(k string) (string, bool) {
    c.mu.RLock(); defer c.mu.RUnlock()
    v, ok := c.m[k]
    return v, ok
}
func (c *Cache) Set(k, v string) {
    c.mu.Lock(); defer c.mu.Unlock()
    c.m[k] = v
}
func NewCache() *Cache {
    return &Cache{m: make(map[string]string)}
}

Почему: RLock допускает параллельных читателей, обычный Lock исключает всех на время записи, а конструктор создаёт map до первого Set.

15Инициализация через Oncesync.Once + goroutines

Условие

Десять горутин запрашивают конфигурацию. Дорогая загрузка должна выполниться ровно один раз.

type Loader struct {
    once sync.Once
    cfg Config
    err error
}

Решение

func (l *Loader) Get() (Config, error) {
    l.once.Do(func() {
        l.cfg, l.err = loadConfig()
    })
    return l.cfg, l.err
}

results := make(chan Config, 10)
for i := 0; i < 10; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        cfg, _ := loader.Get(); results <- cfg
    }()
}
wg.Wait(); close(results)

Почему: Once публикует результат загрузки всем конкурентным вызывающим. Сохранять нужно и значение, и ошибку.

16Флаг atomic.BoolСостояние ≠ жизненный цикл

Условие

После критической ошибки workers должны пропускать новые jobs. Используй атомарный флаг и корректно заверши workers.

var stopped atomic.Bool
jobs := make(chan Job)

Решение

for i := 0; i < 4; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for job := range jobs {
            if stopped.Load() { continue }
            if handle(job) != nil { stopped.Store(true) }
        }
    }()
}
sendJobs(jobs); close(jobs)
wg.Wait()

Почему: atomic убирает race на флаге, но не закрывает канал и не прерывает I/O. Для немедленной отмены нужен context.

17Очередь через sync.CondWait + Signal + Mutex

Условие

Реализуй очередь: Take блокируется, пока producer не добавит элемент через Put.

type Queue struct {
    mu sync.Mutex
    ready *sync.Cond
    items []int
}

Решение

func NewQueue() *Queue {
    q := &Queue{}
    q.ready = sync.NewCond(&q.mu)
    return q
}
func (q *Queue) Put(v int) {
    q.mu.Lock()
    q.items = append(q.items, v)
    q.ready.Signal()
    q.mu.Unlock()
}
func (q *Queue) Take() int {
    q.mu.Lock(); defer q.mu.Unlock()
    for len(q.items) == 0 { q.ready.Wait() }
    v := q.items[0]; q.items = q.items[1:]
    return v
}

Почему: Wait атомарно отпускает lock и снова захватывает его после пробуждения. Условие проверяется в цикле.

18Конфиг через atomic.PointerLock-free чтение snapshot

Условие

Readers часто читают неизменяемый Config, updater получает новые версии из канала. Чтение должно быть без Mutex.

var current atomic.Pointer[Config]
// updates - канал новых Config

Решение

current.Store(&Config{Timeout: time.Second})
wg.Add(1)
go func() {
    defer wg.Done()
    for cfg := range updates {
        next := cfg
        current.Store(&next)
    }
}()

cfg := current.Load()
use(cfg.Timeout)
close(updates); wg.Wait()

Почему: атомарно заменяется указатель на полностью созданный snapshot. После публикации объект нельзя изменять.

19Пул: atomic + MutexРазным данным — разные примитивы

Условие

Worker pool считает успехи атомарно, складывает ошибки в общий slice под Mutex и отдаёт результаты через канал.

var okCount atomic.Int64
var mu sync.Mutex
var errs []error

Решение

for i := 0; i < workers; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for job := range jobs {
            r, err := process(job)
            if err != nil {
                mu.Lock()
                errs = append(errs, err)
                mu.Unlock()
                continue
            }
            okCount.Add(1)
            results <- r
        }
    }()
}
go func() { wg.Wait(); close(results) }()
for r := range results { save(r) }

Почему: atomic подходит независимому числу, Mutex — составному slice. Канал закрывается после завершения всех отправителей.

20Завершение всей системыContext + atomic + Mutex + WaitGroup

Условие

Сервис обрабатывает jobs четырьмя workers, считает активные операции атомарно и статистику под Mutex. По cancel всё должно завершиться.

type Stats struct {
    mu sync.Mutex
    byType map[string]int
}
func Run(ctx context.Context, jobs <-chan Job)

Решение

func Run(ctx context.Context, jobs <-chan Job) {
    var wg sync.WaitGroup
    var active atomic.Int64
    stats := Stats{byType: make(map[string]int)}
    for i := 0; i < 4; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for {
                select {
                case <-ctx.Done(): return
                case job, ok := <-jobs:
                    if !ok { return }
                    active.Add(1)
                    kind := process(ctx, job)
                    active.Add(-1)
                    stats.mu.Lock()
                    stats.byType[kind]++
                    stats.mu.Unlock()
                }
            }
        }()
    }
    wg.Wait()
}

Почему: context просит workers остановиться, WaitGroup подтверждает их выход, atomic хранит независимый счётчик, а Mutex защищает map. Сама process тоже должна учитывать context.
