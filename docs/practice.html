01Запуск и ожидание горутинgo + sync.WaitGroup

Условие

Запусти три вызова work конкурентно и дождись каждого. Порядок вывода не фиксирован.

func work(id int) { fmt.Println("worker", id) }

func main() {
    // work(1), work(2), work(3) конкурентно
}
  • Add должен выполняться до запуска горутины.
  • Каждый worker обязан сообщить о завершении.

Решение

var wg sync.WaitGroup
for i := 1; i <= 3; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        work(id)
    }(i)
}
wg.Wait()

Почему: Wait блокирует main, пока счётчик не станет нулём. WaitGroup ждёт выполнение, но не защищает общие данные.

02Результат через каналНебуферизованный channel

Условие

Вычисли квадрат числа в горутине и передай результат в main через канал.

func square(n int, out chan<- int) {
    // отправь n * n
}

Решение

func square(n int, out chan<- int) { out <- n * n }

result := make(chan int)
go square(7, result)
fmt.Println(<-result) // 49

Почему: send и receive на небуферизованном канале встречаются и синхронизируют две горутины. Для одного чтения закрывать канал необязательно.

03Кто закрывает канал?close + range

Условие

Producer отправляет числа 1…5. Consumer читает их через range и должен завершиться.

func produce(out chan<- int) {
    for i := 1; i <= 5; i++ { out <- i }
    // чего не хватает?
}

Решение

func produce(out chan<- int) {
    defer close(out)
    for i := 1; i <= 5; i++ { out <- i }
}

ch := make(chan int)
go produce(ch)
for v := range ch { fmt.Println(v) }

Почему: канал закрывает отправитель — именно он знает, что новых значений не будет. range дочитает буфер и завершится.

04Буфер и backpressureОграниченная очередь

Условие

Создай очередь максимум на три задания. Если consumer отстаёт, producer должен ждать.

type Job struct{ ID int }
jobs := make(chan Job, /* размер */)

Решение

jobs := make(chan Job, 3)
go func() {
    defer close(jobs)
    for i := 1; i <= 10; i++ {
        jobs <- Job{ID: i}
    }
}()
for job := range jobs { handle(job) }

Почему: пока в буфере есть место, producer идёт дальше. Когда три места заняты, следующий send ждёт consumer — это естественное обратное давление.

05Ожидание через selectРезультат или timeout

Условие

Получи результат, но не жди дольше 500 мс. Таймер должен корректно освобождаться.

func wait(result <-chan string) {
    // result или timeout
}

Решение

func wait(result <-chan string) {
    timer := time.NewTimer(500 * time.Millisecond)
    defer timer.Stop()
    select {
    case v := <-result:
        fmt.Println(v)
    case <-timer.C:
        fmt.Println("timeout")
    }
}

Почему: select ждёт готовый case. default здесь не нужен: в цикле он создал бы активное ожидание и нагрузку на CPU.

06Отмена через contextУправление жизненным циклом

Условие

Worker обрабатывает задания, пока не отменён context или не закрыт входной канал.

func worker(ctx context.Context, jobs <-chan Job) {
    for { /* жди ctx.Done() или jobs */ }
}

Решение

func worker(ctx context.Context, jobs <-chan Job) {
    for {
        select {
        case <-ctx.Done():
            return
        case job, ok := <-jobs:
            if !ok { return }
            handle(job)
        }
    }
}

Почему: ctx.Done() закрывается при отмене. Проверка ok не даёт бесконечно читать zero value из закрытого канала.

07Фиксированный worker poolЧетыре постоянных worker

Условие

Обработай 100 задач максимум четырьмя workers и собери результаты. results закрой только после завершения всех отправителей.

func worker(jobs <-chan Job, results chan<- Result) {
    for job := range jobs { results <- process(job) }
}

Решение

jobs := make(chan Job)
results := make(chan Result)
var wg sync.WaitGroup
for i := 0; i < 4; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        worker(jobs, results)
    }()
}
go func() { wg.Wait(); close(results) }()
go func() { defer close(jobs); sendJobs(jobs) }()
for r := range results { save(r) }

Почему: четыре workers задают лимит активной обработки. Отдельная closer-горутина ждёт всех отправителей, пока main одновременно читает результаты.

08Лимит через семафорНе более пяти операций

Условие

Для каждого URL запусти горутину, но разреши одновременно выполнять максимум пять запросов.

func fetchAll(urls []string) {
    sem := make(chan struct{}, /* лимит */)
}

Решение

func fetchAll(urls []string) {
    sem := make(chan struct{}, 5)
    var wg sync.WaitGroup
    for _, url := range urls {
        wg.Add(1)
        go func(u string) {
            defer wg.Done()
            sem <- struct{}{}
            defer func() { <-sem }()
            fetch(u)
        }(url)
    }
    wg.Wait()
}

Почему: шестая горутина ждёт свободный слот. В отличие от worker pool, горутин может быть много, но одновременно выполняется не больше пяти запросов.

09Объединение потоков fan-inНесколько входов → один выход

Условие

Объедини произвольное число входных каналов в один. Закрой выход после исчерпания всех входов.

func merge(inputs ...<-chan int) <-chan int {
    out := make(chan int)
    // copier для каждого input
    return out
}

Решение

func merge(inputs ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    wg.Add(len(inputs))
    for _, in := range inputs {
        go func(ch <-chan int) {
            defer wg.Done()
            for v := range ch { out <- v }
        }(in)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

Почему: отдельный copier читает каждый источник. Порядок между источниками не гарантирован, а выход закрывается ровно после последнего copier.

10Безопасный pipelineОтмена без утечки горутин

Условие

Построй стадию square. Если sink прекратил чтение, context должен разблокировать и чтение, и отправку результата.

func square(ctx context.Context, in <-chan int) <-chan int {
    out := make(chan int)
    // стадия pipeline
    return out
}

Решение

func square(ctx context.Context, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for {
            select {
            case <-ctx.Done():
                return
            case v, ok := <-in:
                if !ok { return }
                select {
                case out <- v * v:
                case <-ctx.Done(): return
                }
            }
        }
    }()
    return out
}

Почему: проверять отмену нужно и вокруг потенциально блокирующего send. Стадия владеет своим out и закрывает его при завершении.
